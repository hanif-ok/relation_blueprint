# Quick Task 260903-d77: Fix the marquee hit-test coordinate space — Summary

The rubber band was captured in SCREEN pixels but hit-tested against WORLD-space object boxes, so
banding was only ever correct at the untouched initial view; it drifted further wrong the more the
curator panned or zoomed. Fixed by converting the band through a new pure `screenBoxToWorld` helper
at release time, and closed the hole that let the defect ship twice by adding regression tests at
non-identity Stage views.

## What Was Built

**Task 1 — the fix (commit `ebbe623`)**

- `marquee.ts` exports `StageViewport { x, y, scale }` and
  `screenBoxToWorld(box, view)`: `x = (box.x − view.x)/scale`, `y = (box.y − view.y)/scale`,
  extents divided by `scale`. Declared locally rather than reusing `useViewportCulling.StageView`,
  which carries pixel width/height the band does not need and lives in a React+Konva module.
- A zero or non-finite `scale` is treated as 1 (**T-D77-01**), the same guard in the same form as
  `getVisibleRect` and `coords.stageToImage`. A non-finite **pan** is deliberately unguarded
  (**T-D77-02**): it propagates into the box, where `marqueeHits`' existing `isFiniteBox` check
  (T-QT-03) degrades it to an empty selection.
- `MapView.finishMarquee` converts the normalized band before `marqueeHits`, reading the live view
  off the already-declared `stageRef` and falling back to `{0,0,1}` when it is null (identical to
  the previous behaviour). `stageRef` is a ref, so the callback's dependency array is unchanged.
- Left alone on purpose: `MARQUEE_MIN_DRAG` still gates on **raw screen px, before** the conversion
  (**T-D77-03**); the DOM band overlay still reads raw `marquee.x0/y0/x1/y1` and stays a
  constant-weight 1px outline at any zoom; `MARKER_HALF_EXTENT` needed no change (already a
  world-space half-extent); `groupMove.ts` and `GraphView.tsx` untouched.

**Task 2 — the regression net and the corrected header (commit `6fffc92`)**

- Unit matrix over `screenBoxToWorld`: identity, scale-only, pan-only, both, the `0` / `NaN` /
  `Infinity` scale guards, and the non-finite-pan → empty-selection chain.
- The paired case that documents the defect in one place: the same band at the same panned view
  selects the marker once converted, and selects **nothing** unconverted (the shipped behaviour).
- Two e2e tests that move the Stage **before** banding — one middle-drag pan, one wheel-zoom. Both
  derive the band from the observed `{x, y, scale}` read back off the Stage rather than a hard-coded
  scale, and both assert the view is genuinely non-identity first, so neither can silently pass at
  the identity view and prove nothing.
- `marquee.ts`'s module header rewritten: it names SCREEN and WORLD distinctly, states that the
  module hit-tests in WORLD space, states that the band arrives in SCREEN space and must go through
  `screenBoxToWorld` in `MapView.finishMarquee` after the screen-px click-vs-drag gate, and cites
  `getVisibleRect` as corroboration. `Box` is now documented as space-agnostic;
  `shapeStageBox`/`markerStageBox`/`marqueeHits` docs name WORLD explicitly. MapView's band-state
  comment corrected; the overlay comment was already accurate and was left as-is.

## Key Decisions

1. **Convert the band, not the objects.** The objects' world boxes are what the renderer and the
   culling pass already agree on; moving them into screen space would have meant recomposing every
   candidate per release and would have made `MARKER_HALF_EXTENT` zoom-dependent.
2. **Read the transform at release.** That is what makes the hit-test agree with what is visually
   inside the band at the moment the curator lets go, even after a mid-band wheel-zoom.
3. **Keep the click-vs-drag gate in screen px.** Converting first would make a zoomed-out view read
   real drags as stray clicks and a zoomed-in view read stray clicks as drags — reintroducing the
   original T-QT-01 concern.
4. **No renames.** `shapeStageBox`/`markerStageBox` keep their names; only their docs disambiguate.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's prescribed e2e assertion is vacuous — replaced it**

- **Found during:** Task 2, while RED-checking the new e2e tests against a deliberately
  un-converted build.
- **Issue:** the plan said to reuse the existing spec's Delete-based assertion,
  `page.waitForFunction(async (id) => { … return m.shapes.length === 0; })`. `waitForFunction` does
  **not** await an async predicate — it tests the returned `Promise` for truthiness, which is always
  true, so the wait resolves on its first poll. Proven directly: with the pre-fix band the helper
  read survivors `["shape-a"]` while that exact wait still went green. Shipping regression tests on
  this primitive would have produced tests that can never fail — precisely the failure this task
  exists to prevent.
- **Fix:** the new tests assert with `expect.poll(() => page.evaluate(async … )).toEqual([])`
  (`page.evaluate` does await), which also names the surviving shape on failure.
- **Files modified:** `e2e/canvas-pan-marquee.spec.ts`
- **Commit:** `6fffc92`

**2. [Rule 2 - Missing critical step] The new e2e tests must confirm the bulk-delete dialog**

- **Found during:** Task 2, once assertion 1 was real and the tests began failing *with* the fix.
- **Issue:** a 2+ marquee selection routes through `requestDelete`'s blocking `ConfirmDialog`
  (T-NFS-01, shipped in 260902-nfs) — pressing Delete writes nothing until the dialog is confirmed.
  The plan's Delete-only recipe therefore never deleted anything.
- **Fix:** after `keyboard.press('Delete')` the helper asserts the dialog and its
  `Delete 2 selected objects?` title, then clicks its Delete button. This made the assertion
  *sharper* than the plan's: a band catching only one rect takes the immediate single-delete path
  and never opens a dialog at all, so the wrong-selection case now fails on the dialog assertion
  before any write.
- **Files modified:** `e2e/canvas-pan-marquee.spec.ts`
- **Commit:** `6fffc92`

**3. [Rule 2 - Missing critical step] Non-vacuity guard on the seed**

- **Issue:** "the map ends up empty" only means something if it started with both rects; a silently
  failed seed would make the assertion pass trivially.
- **Fix:** the helper asserts `['shape-a','shape-b']` are present before banding.
- **Commit:** `6fffc92`
