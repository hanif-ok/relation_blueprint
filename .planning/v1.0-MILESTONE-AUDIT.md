### BLOCKER detail — fieldDefs never reach the cloud

**Confirmed by source read (orchestrator-verified):**
- `src/sync/syncEngine.ts:73` — `ENTITY_TYPES = ['people','maps','markers','groups','relationship-links']` — **no `'field-defs'`**.
- `bootstrap()` (`:112`), `commit()` (`:184`), `reconcileOnOpen()` (`:246`) iterate `ENTITY_TYPES` / `dirtyTypes`. `serializeShards` *does* produce `field-defs-000.json` (`src/sync/serializer.ts:55`) but nothing writes or reads it on the cloud path — it is generated in memory and discarded.
- `getDirtyTypes()` never checks `db.fieldDefs`; `markSynced()` transaction omits `db.fieldDefs`.
- `ManifestSchema` (`src/domain/schemas.ts`) has no fieldDefs shard pointer.
- The serializer's own comment (`serializer.ts:23-27`) asserts fieldDefs "ride in export/restore + reconcile" — **true for export/restore, false for reconcile/push.**

**Impact:** Single-device usage is unaffected (Dexie is the runtime source of truth). Local export → restore is unaffected (handled directly). The break bites the *cloud durability* guarantee: a second device, or a fresh browser session reconnecting to Drive (the "cloud is the only copy" scenario this project is built around), pulls entity custom *values* with no *definitions* to render or validate them. Directly undercuts DATA-03 and the core "own your entire database in your own cloud" value.

**Single fix target:** add `'field-defs'` to the manifest sync machinery (ENTITY_TYPES + getDirtyTypes + reconcileOnOpen + markSynced txn) and a fieldDefs pointer to ManifestSchema; add a regression test proving push-then-fresh-reconcile round-trips a field definition.
