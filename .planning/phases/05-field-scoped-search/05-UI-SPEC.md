# Phase 5 — UI Design Contract

> Visual and interaction contract for Field-Scoped Search (the signature feature). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> This phase adds **ZERO new foundational tokens** — it inherits the locked visual language from `01-UI-SPEC.md` (`src/app/tokens.ts` + `tokens.css`). What is new is a **single DOM surface** (a "Search" view) composed almost entirely of existing parts: the `ViewSwitcher` rail entry, the `BrowseRow`/windowed-list pattern, and `ProfileSidebar` on click. The only net-new visual primitives are a **search input**, a **field-scope checkbox panel**, and a **matched-field snippet with a highlighted term** on the result row's secondary line.

---

## Design Direction (this phase's point of view)

Phase 5 makes the database **legible by attribute, and makes the scoping *visible*.** The through-line from the established product:

- **Search is a first-class view, not a chrome accessory.** It is a sibling of People/Graph in the left rail (D-01) — not a top-bar box, not a filter bolted onto the People browse list. It reuses the single-surface-swap pattern (Phase 2 D-13) so search feels like "a place you go," consistent with every other view.
- **The scoping must be seen to be believed.** The whole point is "smith" matches names but not blacksmiths' jobs. Two mechanisms make the mechanism visible: the **field-scope checkbox panel** (the control) and the **matched-field snippet** on each result row (the evidence — `job: black[smith]` with the term highlighted). The user unchecks "job," and the blacksmiths vanish — and they can *see why* on the rows that remain.
- **Subtractive by default.** Every searchable attribute starts ON (D-04); scoping is an act of *removal*. This matches the mental model in the signature example ("turn the job field off").
- **Reuse over invent.** A result row IS a `BrowseRow` (thumbnail + name + secondary line), click opens `ProfileSidebar`, "Show on map" reuses the existing spatial action, and the scope preference persists in the existing Dexie meta store. The one new dependency is `minisearch` (MIT) — a build-time lib, no data-model change, no cloud/backup change.
- **Calm, paper-chrome surface.** Search is a DOM view on **paper** (`#F4F1EA`) — it never touches the slate canvas. No amber except the inherited focus-ring on interactive controls; there is no "create" act here, so the accent budget stays untouched.

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Snippet `field:` prefix → value gap; checkbox → label gap; tag-chip inner padding (reused) |
| sm | 8px | Checkbox-row vertical stacking; input icon → text gap; result-row secondary-line top gap |
| md | 16px | Search-view padding; input internal padding; gap between scope panel and results column |
| lg | 24px | Section separation (input block → results region); scope-panel outer padding |

## Typography

Inherited unchanged. Four roles; heading/display line-height 1.2, body 1.5. Exactly two Inter weights (400 + 600) + Fraunces 560.

| Role | Family | Size | Weight | Line Height | Usage in this phase |
|------|--------|------|--------|-------------|---------------------|
| Display | Fraunces | 28px | 560 | 1.2 | Pre-query / zero-match / all-fields-off state heading |
| Heading | Inter | 20px | 600 | 1.2 | (not prominently used — the view has no page title bar beyond the rail; reserved if a header is added) |
| Body | Inter | 16px | 400 | 1.5 | Search input text; result-row name (reused `BrowseRow` name); state sub-lines |
| Label | Inter | 13px | 600 | 1.35 | "Search in:" eyebrow (uppercase +0.04em, matching "Appears on"/"Relationships"); checkbox labels; the matched-field snippet's `field:` prefix |

**Matched-field snippet typography.** The snippet on the result row's secondary line is **Label/13 ink-muted** (matches the existing `rowSecondary` treatment). Structure: a **`field:` prefix** (Label 13, ink-muted, e.g. `job:`) + the matched value fragment (13px, ink-muted) with the **matched substring wrapped in `<mark>`** — see Color for the highlight treatment. The matched term inside `<mark>` renders at the same 13px but with an **amber-tinted highlight background + ink text at weight 600** for emphasis. The input placeholder is Body/16 ink-muted.

**XSS boundary (inherited, non-negotiable):** the snippet, the highlighted term, the field label, and the entity name all render as **React children** — the matched substring is wrapped in a real `<mark>`/`<span>` element, **never `dangerouslySetInnerHTML`** (T-03-01; a leaked Drive token is the modeled threat). User-supplied field values must never be injected as HTML.

## Color

No new foundational colors. Search is a **paper-chrome DOM view** — it lives entirely inside the inherited 60/30/10 split; there is no canvas content treatment this phase.

| Role | Value | Usage this phase |
|------|-------|------------------|
| Dominant (60%) | `#F4F1EA` paper | Search-view background, input fill, results column |
| Secondary (30%) | `#E7E2D6` paper-shade | Scope-panel well background; hover fill on result rows / checkbox rows; tag chips (reused); initials-fallback thumbnail |
| Accent (10%) | `#C8742B` amber | **Focus ring only** on the input, checkboxes, and interactive rows (inherited `:focus-visible`) + the **matched-term highlight** (see below). No amber "create" act exists in this view. |
| Destructive | `#B23A2E` brick | Not used in this phase (search authors/deletes nothing). |
| Ink / muted | `#26211A` / `#6B6358` | Row name (ink); snippet, checkbox labels, meta, placeholder (ink-muted) |
| Hairline | `#D8D2C4` | Input border; scope-panel border; row separators |

**Amber (`#C8742B`) usage this phase — still selection/emphasis only, consistent with the marker rule:**
1. The inherited **`:focus-visible` ring** on the search input, checkboxes, and result rows (keyboard focus).
2. The **matched-term highlight** — the substring of a value that MiniSearch matched, rendered in a `<mark>` with an **amber-tint background** `rgba(200,116,43,0.18)` and **ink text at weight 600** (the highlight is the "evidence" that scoping worked — this is emphasis, the amber-family equivalent of selection). Contrast: ink `#26211A` on the amber-tinted-over-paper background ≈ AA+ for 13px text.

Amber is **never** used for: the search input's default (unfocused) border, checked-checkbox fills (checked = ink/`#26211A` check on paper-shade, NOT amber — checking a scope box is not a "create" act), the nav item when the Search view is active (active nav = ink text + 3px ink-muted left bar, inherited U1/A8), or result-row hover (hover = paper-shade fill).

**Checkbox visual treatment:** unchecked = paper fill + hairline border; checked = **ink `#26211A`** box with a paper checkmark (or an ink-accented native checkbox via `accent-color: var(--ink)`). This keeps the scope panel calm and reserves amber strictly for focus + match-highlight. Rationale in Assumptions B3.

## Per-Surface Component Specs & States

### S1 — Search input
- **Placement:** top of the Search view, full-width within the view's `md` (16px) padding, min-height **44px**. A decorative Lucide `Search` glyph (16px, ink-muted, `aria-hidden`) sits at the leading inside edge; text begins after it.
- **Styling:** paper fill, hairline border, `radius-md`; `:focus-visible` → amber ring (inherited). Reuses the `.input` treatment established in `PersonPicker.module.css` (paper fill, hairline, focus ring) — extend/share, do not reinvent.
- **Behavior:** **live as-you-type, debounced** (D-02; debounce interval is planner discretion, ~150–250ms suggested). Queries run **on the main thread** via MiniSearch (D-02). **Results begin at the 2nd typed character** (D-08) — at 0–1 chars the view shows the pre-query prompt (S4), never the whole DB.
- **Accessibility:** `<input type="search">` with an associated visually-labelled or `aria-label`ed control (**"Search people"**); wire `aria-controls` → the results list and `role="searchbox"` semantics are native. Announce result count changes via a visually-hidden `aria-live="polite"` region (**"{n} people match"** / **"No people match"**) so AT users hear results update as they type (mirrors the sidebar's live-region pattern).
- **Optional polish (NOT required):** a "/" keyboard shortcut to focus the input — deferred (CONTEXT Claude's-discretion; not decided). If added, it must not trap focus and must be discoverable.

### S2 — Field-scope checkbox panel (the signature control)
- **Placement:** a labelled region beside (wide viewports) or above (narrow) the results column. An uppercase Label eyebrow **"Search in:"**, then a vertical checkbox list in a paper-shade well (`radius-md`, hairline). Layout (fixed sidebar vs. collapsible) is planner discretion per CONTEXT — default to a **fixed left column on wide, collapsible `<details>` above results on narrow**.
- **Semantics:** a native `<fieldset>` with a visually-hidden `<legend>` "Search in fields"; each item is a `<label>` wrapping a native `<input type="checkbox">` + the field label. The whole label row is the click target (≥24px).
- **The field list (D-03):** the built-in People attributes **Name, Phone, Description, Tags, Notes** + **every custom field defined on People** (live from the `FieldDef` schema). Excluded: **Photo/gallery** (no text). Number/date custom values are stringified for indexing; `link-to-entity` fields are indexed by the target entity's display name (D-03) — the checkbox still uses the field's own label.
- **Default & persistence (D-04/D-05):** **ALL fields ON by default**; scoping is **subtractive** (uncheck to exclude). The selection **persists across sessions** in the Dexie meta/settings store, **keyed by stable `FieldDef.id`** for custom fields (a rename does not reset it) and by a stable built-in key for built-ins. **Soft-deleted custom fields drop out of the list automatically** (derived live from the schema); their persisted state is simply ignored while absent and honored again if restored.
- **States:**
  - **Custom fields present:** built-ins first, then custom fields (in the schema's field order), so "Job"/"Employer" appear as togglable rows — this is exactly what the blacksmith example scopes against.
  - **No custom fields defined:** only the five built-ins show — still fully functional.
  - **All boxes unchecked:** the panel stays interactive but the results region shows the **all-fields-off guard** (S4) — never a silently-empty result set.
- **Live reactivity:** the checkbox list re-derives when People `FieldDef`s change (add/rename/soft-delete) via the existing live-query path — the panel must not require a reload to reflect a new field.

### S3 — Results list & result row
- **List:** reuses the **windowed 64px-row** pattern from `BrowseList` (cheap at thousands). Same lazy media via `useEntityThumb`, same round-avatar/initials thumbnail for People.
- **Row = `BrowseRow` variant (D-09/D-10):**
  - **Left:** 48px round avatar (or initials fallback) — reused verbatim.
  - **Center name:** Body/16 ink — reused.
  - **Secondary line (the new bit):** a **matched-field snippet** showing **which field matched**, with the matched term **highlighted** — e.g. `job: black⟦smith⟧` (⟦⟧ = `<mark>`). Format: `{fieldLabel}: …{context}{<mark>matched</mark>}{context}…`. Snippet context length is planner discretion (~24–40 chars each side suggested).
    - **When the match is on the Name field:** there is no useful snippet (the name is already the row title) — **fall back to the normal `BrowseRow` secondary line** (tags chips, else "updated Nd ago").
    - **When multiple fields match:** show the **highest-boosted** matched field's snippet (name > tags/phone > description/notes > custom neutral, per D-07); a subtle "+N more" affordance is optional planner discretion.
  - **Right actions (D-10):** **click row → `ProfileSidebar`** (S5, reuses `onOpen`); **"Show on map ↗"** button enabled for People (`isSpatial('people')`, S6, reuses `onShowOnMap`). The overflow Edit/Delete menu is **optional** here — search is a find-and-open surface; planner may include the existing overflow or omit it. Row actions reuse existing wiring verbatim.
- **Ranking (D-07):** field-boosted — **Name highest**, then **Tags/Phone**, then **Description/Notes**, custom fields **neutral default weight**. A name hit outranks a stray notes hit. Exact boost constants are planner tuning discretion.
- **Fuzzy matching (D-06):** MiniSearch `fuzzy` (~0.2, edit-distance scaled to term length) **+ `prefix: true`** so "smi" → "Smith" as you type. Moderate, not aggressive.
- **Incremental index (criterion 3):** the index updates incrementally through the repository change signal (add on create, replace on update, discard on delete) — **not** a full rebuild every load. Mechanism (in-memory rebuild-on-load vs. serialized-cache-in-Dexie) is planner discretion; whatever is chosen, the index is a **derived, rebuildable projection** and never enters the cloud/backup serializer.

### S4 — Search states (mirror `BrowseList`'s careful state handling, D-11)
Three **distinct** states, each visually a centered state panel in the results column (Display/28 heading + Body/16 sub-line + a Lucide glyph, mirroring the `BrowseList` empty pattern — but **no CTA button**, since search creates nothing):

| State | When | Glyph | Heading | Sub-line |
|-------|------|-------|---------|----------|
| **Pre-query prompt** | Query < 2 chars | `Search` (ink-muted, 32px) | **Search people** | **Search people by name, tags, or any field — then narrow it with the checkboxes.** |
| **Zero-match** | Query ≥2 chars, ≥1 field ON, 0 results | `SearchX` (ink-muted, 32px) | **No people match "{query}"** | **Check your spelling, or turn more fields on to widen the search.** |
| **All-fields-off guard** | ≥1 field, but every checkbox OFF | `Filter` / `FilterX` (ink-muted, 32px) | **Nothing to search** | **Every field is turned off. Turn at least one field on to search.** |

- The **all-fields-off guard** is explicitly NOT a zero-match message — it tells the user *why* nothing is searchable rather than showing a mysteriously empty result set (D-11).
- The `{query}` in the zero-match heading renders as a **React child** (never injected HTML).
- **Loading:** MiniSearch is synchronous on the main thread at these scales, so there is typically no async loading state. If a Web-Worker fallback is later added (D-02, only on profiled jank), reuse a quiet "Searching…" shimmer — never a blocking spinner.

### S5 — Result → `ProfileSidebar` (reuse)
- Clicking a result row opens the **existing full `ProfileSidebar`** on that Person (reuses `onOpen`), exactly like a `BrowseRow` in list context. No new panel. Focus moves into the sidebar; the existing `aria-live` "Selected {Name}" announcement is reused.

### S6 — Result → "Show on map" (reuse)
- The result row's **"Show on map ↗"** button reuses the existing spatial action (`onShowOnMap`) — People are spatial (`isSpatial('people') === true`), so it is enabled and navigates to the person's placement on the map. Wiring reused verbatim from `BrowseRow`.

### Accessibility summary
- Search input is a native `searchbox` with an accessible name; the field-scope panel is a native `<fieldset>`/`<legend>` of native checkboxes (full keyboard + AT support with no custom widget).
- Result count changes announced via `aria-live="polite"`.
- Results list rows keep the existing `role="button"` + Enter/Space activation and nested-button hit areas from `BrowseRow`.
- The Search nav item rides the existing `ViewSwitcher` roving-focus group (`aria-current="page"` when active, ink left-bar, `aria-label`/`title` for the icon-only narrow rail). No count pill (`'search'` ∈ `NO_PILL`).

## Dependencies & Risks (for planner)

- **New dependency:** `minisearch` (7.2.x, MIT) must be installed before S1–S3. Pure logic lib; verify no unexpected peer deps.
- **Data-model prerequisite:** **none for the schema** — search is read-only over the existing `people` table + `FieldDef` schema (Type ↔ zod ↔ Dexie triple untouched). The persisted field-scope selection lives in the **existing** Dexie meta/settings store (no new synced entity, no `BackupSchema`/serializer/SyncEngine change). **NOTE: Dexie, not Drizzle — there is NO migration-push step** ([[schema-gate-dexie-false-positive]]).
- **Index lifecycle (planner discretion):** in-memory rebuild-on-load vs. serialized cache in Dexie; and the concrete incremental-update wiring (repository change signal → MiniSearch `add`/`replace`/`discard`). Locked requirement (criterion 3) is only *that* it updates incrementally and stays fast toward thousands — mechanism is planner's (standard MiniSearch territory; roadmap flags skip-research).
- **Custom-field awareness gate:** the scope panel + index must both stay in sync with live People `FieldDef`s (add/rename/soft-delete), keyed by stable `FieldDef.id` — this is the one cross-cutting correctness requirement all surfaces share.
- **Reuse contract:** `ViewSwitcher` (add `'search'` to `ViewKey`/`VIEW_ITEMS`/`NO_PILL`), `BrowseRow`/`BrowseList` windowed list + `useEntityThumb`/`entityTags` helpers, `browseTypes.isSpatial`, `ProfileSidebar`, and the `.input` styling from `PersonPicker.module.css` are all reused — the planner should extend, not fork, these.
