<design_notes>
## Quarantine storage decision — ZERO schema change (PREFERRED path, taken)

`CustomValues = Record<string, CustomValue>` and the zod lock is
`CustomValuesSchema = z.record(z.string(), CustomValueSchema)` — it accepts ANY string key, and a
quarantined original is itself a valid `CustomValue` (string | number | string[] | MediaRef | null).
Therefore: store the quarantined original under a RESERVED, namespaced key inside the SAME `custom`
map (one reserved key per quarantined field id). This means:

- No change to `src/domain/types.ts`, `src/domain/schemas.ts`, `src/db/schema.ts`,
  `src/sync/serializer.ts`, `src/features/backup/exportDb.ts`, or `importDb.ts`. The reserved key
  rides inside the existing `custom` map, which `serializeShards` JSON-stringifies verbatim and
  `BackupSchema` accepts (any string key). Round-trip is automatic.
- The UI never renders the reserved key, because the form/profile only iterate keys that match a
  live `FieldDef.id` (from `listFieldDefs`); a reserved key matches no def.
- D-05 "re-addable / restorable on revert": when a type changes BACK to a type the quarantined
  original fits, the wiring restores from the reserved key and clears it.

Define ONE exported helper to build the reserved key from a field id (e.g.
`quarantineKey(fieldId)` returning a stable namespaced string) and ONE exported constant for the
namespace prefix, both in `src/db/repository.ts`, so the key shape is single-sourced and a future
Phase-5 search indexer can skip reserved keys by prefix. Do NOT hand-roll the prefix at each call
site.

## Transaction ordering (mid-change failure safety)

`applyFieldTypeChange` must run the entity coercion AND the `updateFieldDef` type patch so a
mid-change failure cannot leave the def changed but values un-coerced (or vice-versa). Put the
`updateFieldDef` write and the per-entity coercion writes in a story where the def patch is applied
in the SAME logical unit as the value rewrite. Since `updateFieldDef`, `updatePerson`, etc. each open
their own transaction + emit, the safest concrete shape is: `applyFieldTypeChange` opens ONE rw
transaction over the affected entity table AND `db.fieldDefs`, rewrites the def `type` (and any other
patched fields) plus every entity's coerced/quarantined value inside it, stamping `updatedAt`/`dirty`
on each touched row, and emits the change events AFTER the transaction commits. `FieldEditor.handleSave`
then calls `applyFieldTypeChange` INSTEAD OF `updateFieldDef` when the type changed, and the existing
`updateFieldDef` path only when the type is unchanged. Read the existing `deleteEntity` (lines ~172-206)
and `reorderFieldDefs` (lines ~476-486) for the established single-rw-transaction-then-emit shape; mirror
it. Do NOT do raw `table.put` that bypasses the dirty/updatedAt stamping or the emit — coerced values
MUST sync to cloud.
</design_notes>
