## Phase Goal

**As a** single curator, **I want to** model my world fully — defining custom typed fields on any entity and working with all four first-class object types (People, Locations/Maps, Groups, Relationship-links) — and browse people and locations as lists, **so that** my whole world is captured in rich, typed records I fully own.

## Acceptance Criteria (this plan — the data-model spine)
- [ ] Group, Relationship-link, and rich Location entities create/update through the repository and persist to Dexie.
- [ ] Each entity carries a `custom` value map; custom values round-trip through zod -> Dexie -> serializer -> export/restore.
- [ ] Field definitions (per-type schema) create/reorder/soft-delete through the repository against a `fieldDefs` table keyed by stable id.
- [ ] Export then import the whole DB (5 entity types + fieldDefs + media) reconstitutes it byte-for-byte.

<objective>
Lay the complete, non-retrofittable data backbone for the full entity model so every later slice in this phase has real types, schemas, tables, repository CRUD, and storage threading to build on. This promotes the skeleton `MapDoc` into a rich Location (D-07), introduces Group (D-09) and Relationship-link (D-08) as first-class entity types, adds a per-entity `custom` value map that carries DATA-03 custom-field values (D-01), and introduces a `fieldDefs` table holding the per-type custom-field schema with stable ids and soft-delete (D-02/D-05). It threads all of this through the sharded serializer, the Dexie sync port, and export/restore so the cloud copy and backups stay complete — without adding a second atomic commit point.

Purpose: This is the keystone the whole phase depends on (search, profiles, relationships all build on the typed-field model). It is deliberately a data/spine slice because the four UI slices that follow (browse, delete-split, custom fields, lightbox) cannot exist without it. Its user-facing proof is exercised through the repository + round-trip tests rather than chrome; the chrome arrives in plan 02.
Output: Extended domain types/schemas, the Dexie version(2) tables, repository CRUD for the new types + field-definitions, serializer/sync/backup threading, and the unit + round-trip tests that prove it.
</objective>

## Interface Context for Executors

This plan extends the Phase 1 backbone, all of which is in `src/`:
- **Single mutation path** (`src/db/repository.ts`): every create/update does `Schema.parse({...input, id: nanoid(), updatedAt: Date.now(), dirty: true})` -> `db.<table>.put(x)` -> `emit({entityType, entityId, op})`. Replicate verbatim for the new types.
- **Type <-> schema <-> Dexie correspondence** (`types.ts` <-> `schemas.ts` <-> `db/schema.ts`): every type appears in all three, with the `satisfies` lock at the bottom of `schemas.ts`.
- **Per-type sharding** (`serializer.ts`): `SHARD_NAMES` + `EntitySet` + serialize/deserialize, one `-000` bucket per type; `ManifestSchema.shards` is a `Record<EntityType, ShardPointer>` with explicit per-type keys.
- **Dexie sync port** (`syncEngine.ts:279` `createDexieRepoPort`): `getEntities`/`getDirtyTypes`/`markSynced`/`upsert` read/write per table; `RepositoryPort` + `EntitySet` are the contracts.
- **Export/restore** (`exportDb.ts` / `importDb.ts` + `BackupSchema`): `Backup.entities` holds per-type arrays; `localManifest` builds empty shard pointers; `importDb` validates via `BackupSchema.parse` before one rw transaction.

**Location = enriched `maps` table.** Keep the `EntityType` member `'maps'` and the `markers.mapId` FK unchanged; UI labels it "Locations" later (plan 02). Enrich `MapDoc` with `photo?`, `gallery`, `notes?`, `custom` (and keep `background`/`width`/`height`). This avoids a data migration and an FK rename.
