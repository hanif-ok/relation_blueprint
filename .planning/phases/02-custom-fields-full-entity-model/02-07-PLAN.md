<objective>
Close the CR-01 BLOCKER raised by the 02-06 code review (02-REVIEW.md): `coerceEntityCustom` stores
every quarantined original under ONE reserved key per field (`quarantineKey(fieldId)`) and overwrites
it unconditionally, so a SECOND quarantining type change permanently destroys an already-quarantined
original — the exact D-05 "set aside, NOT deleted, restorable on revert" guarantee that plan 02-06
exists to deliver. Reachable through ordinary curation: quarantine "hello" (text→number) → enter 5 in
the number field → number→date quarantines 5 and clobbers "hello".

Fix: key quarantined originals by their SOURCE field-type — `quarantineKey(fieldId, sourceType)` —
so at most one original exists per (field, sourceType) and successive quarantines from different
source types never collide. Restore resolves from the TARGET type's key, which is unambiguous and
also closes the co-located WARNING about the restore branch judging fitness off the in-flight type
pair. Add a multi-hop regression test (the gap the single-cycle 02-06 test missed). Separately, guard
the profile tags read path against a non-array value (the second WARNING).

Purpose: This is a silent USER-DATA-LOSS defect in an app whose entire premise is "you fully own your
data." It must be closed before phase 02 can be called complete. The fix stays within the 02-06
zero-schema-change design (each reserved key still holds a single CustomValue valid under
CustomValuesSchema).

Output: A re-keyed `quarantineKey`/`coerceEntityCustom`, a multi-hop preservation+restore test, and a
guarded tags read row. No schema/serializer/backup change.
</objective>

<design_notes>
## Source-type-keyed quarantine — still ZERO schema change (the fix)

Today: `QUARANTINE_KEY_PREFIX = '__quarantine:'` and `quarantineKey(fieldId) = '__quarantine:<fieldId>'`.
ONE slot per field → a second quarantine overwrites the first (the BLOCKER).

Fix: extend the reserved key with the SOURCE field-type:
`quarantineKey(fieldId, sourceType) = '__quarantine:<fieldId>:<sourceType>'`. A nanoid `FieldDef.id`
contains only `[A-Za-z0-9_-]` (no colon), and `FieldType` values
(`text|number|date|phone|tags|link-to-entity|photo`) contain no colon, so the key parses
unambiguously and still begins with `QUARANTINE_KEY_PREFIX` (a future Phase-5 search indexer skips it
by prefix exactly as before). Each key still holds a SINGLE `CustomValue`, so `CustomValuesSchema =
z.record(z.string(), CustomValueSchema)`, `serializeShards`, and `BackupSchema` all round-trip with NO
change to types/schemas/serializer/backup — identical zero-schema invariant to 02-06.

`coerceEntityCustom` rewrite (preserve-all):
- STORE: when the live value does not fit `toType`, put the untouched original under
  `quarantineKey(fieldId, fromType)` (its source type) and clear the live value. This can never clobber
  an original set aside from a DIFFERENT source type.
- RESTORE: after the store step, look up `quarantineKey(fieldId, toType)` — the original that was set
  aside when this field last WAS `toType`. Such a value fits `toType` by construction; restore it to
  the live value and delete that one key. (Restoring by the target key is what removes the in-flight
  from→to ambiguity the WARNING flagged — a value quarantined from text is only ever restored when the
  field returns to text.)
- The `qKey` is therefore computed per source/target type INSIDE `coerceEntityCustom`; remove the
  single `const qKey = quarantineKey(fieldId)` precomputed at `applyFieldTypeChange` (~line 553) and
  the `qKey` parameter from `coerceEntityCustom` — pass `fieldId, fromType, toType` and let the helper
  build the two keys it needs via the 2-arg `quarantineKey`.

No migration: the quarantine feature shipped in plan 02-06 within this same un-released milestone, so
no real database holds a legacy bare `__quarantine:<fieldId>` key; the reshape only affects dev/test
data. Do NOT add legacy-key handling — it is dead scope.

## IN-01 (info, fold into Task 1)
`coerceEntityCustom` decides `changed` for the kept branch by reference identity
(`result.kept !== next[fieldId]`). `coerceOnTypeChange` returns the same reference for an unchanged
value, so this is correct today — add a one-line comment pinning that contract so a future refactor of
`coerceOnTypeChange` does not silently break the dirty-flag accounting.
</design_notes>
