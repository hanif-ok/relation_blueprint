## Phase Goal

**As a** single curator, **I want to** model my world fully — defining custom typed fields on any entity and working with all four first-class object types — and browse people and locations as lists, **so that** my whole world is captured in rich, typed records I fully own.

## Acceptance Criteria (this plan — the DATA-03 custom-field keystone)
- [ ] Define custom typed fields (all 7 types) on any entity type via a per-type field manager.
- [ ] Custom fields render in profiles (read) and as typed inputs in forms (edit), validated by type + required.
- [ ] Field removal is a soft-delete; re-adding restores stored values.
- [ ] link-to-entity is a one-way pointer; "(removed)" for a missing target.

<objective>
Deliver the signature custom-field system end-to-end: a per-type field manager (D-02/D-03) where a user creates/edits/reorders/soft-deletes typed field definitions, those fields rendering by type in profiles (S15) and as typed, validated inputs in entity forms (S16). It covers all 7 DATA-03 field types (text, number, date, phone, tags/select, link-to-entity, photo) with zod type-checking + an optional per-field `required` toggle as the only validation (D-06), soft-delete that retains values for restore (D-05), and link-to-entity as a one-way pointer with graceful "(removed)" handling (D-10). Custom values are keyed by the field def's stable id and ride on each entity's `custom` map (already round-tripping from plan 02-01).

Purpose: This is DATA-03 — the keystone the whole product (search, profiles, relationships) depends on. It is a vertical slice layered onto the entity forms + profiles + field-def store built in earlier plans: after it, a real user can shape any entity type with their own typed fields and see them validate and render. It is its own plan because the typed value/validation logic + four render/input surfaces is a full slice on its own.
Output: The field manager + editor, the custom-value validate/coerce module, the custom read rows + form inputs, ProfileSidebar/EntityForm/App wiring, and the custom-value unit + custom-fields E2E.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user custom values + field labels/options -> render (profile, form, browse) | Many new user-controlled render paths introduced by custom fields |
| link-to-entity id (untrusted reference) -> resolve + render | A stored id may point at a deleted or wrong-type entity |
| custom value -> zod -> Dexie -> serializer -> export/restore | Custom values must validate without poisoning the manifest/backup schema |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Information Disclosure (XSS) | CustomFieldRows / CustomFieldInputs / field labels + values | mitigate | Every custom value, label, option, and link label rendered as React children — never `dangerouslySetInnerHTML` (an XSS could exfiltrate the in-memory Drive token) — this is the highest-value threat for this phase |
| T-03-06 | Tampering | link-to-entity pointing at a missing/wrong-type entity | mitigate | Resolve the target through a live Dexie read and type-check it before render; render muted "(removed)" rather than a broken link or wrong entity (D-10) |
| T-02-02 | Tampering (schema poisoning) | custom value shape entering Dexie/backup | mitigate | `validateCustomValue` + `CustomValueSchema` (closed union) gate writes; an out-of-band value is rejected, never persisted |
</threat_model>
