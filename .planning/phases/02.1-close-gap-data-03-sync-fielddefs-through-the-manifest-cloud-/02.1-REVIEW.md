## Summary

This phase threads custom-field DEFINITIONS (`db.fieldDefs`) through the cloud manifest path to close the DATA-03 BLOCKER. The implementation is well-targeted and the design invariants from the phase context are all honored correctly:

- The core `EntityType` union in `types.ts` is NOT widened — `'field-defs'` lives only in the sync-local `SyncShardType` token (verified line 45, syncEngine.ts).
- The `ManifestSchema` `'field-defs'` pointer is correctly `.optional()` (schemas.ts:151), and a PRESENT pointer is still fully validated by `ShardPointerSchema` — the untrusted-at-rest gate stays strict (test at entityModel.schemas.test.ts:183 proves this).
- The OLD-manifest missing-pointer branches are guarded in three places: `commit` (line 209-210), `reconcileOnOpen` (line 272), and the watermark loop (line 294). A pre-fix cloud manifest reconciles as a safe no-op rather than crashing.
- Atomicity (STOR-05) is preserved: the field-defs shard flows through the same single-commit-point machinery, and the failure-injection test now seeds a dirty `FieldDef`.

All 26 tests in the three phase test files pass, `tsc --noEmit` is clean, and the `satisfies` compile-time locks confirm each zod schema matches its hand-written interface.

No Critical issues found. The findings below are correctness-adjacent robustness gaps and quality items. The most material is WR-01: a structural fragility in `SHARD_NAMES` (duplicate-value keys) that is currently safe only because no caller iterates the object — a latent trap for future code.

## Warnings

### WR-01: `SHARD_NAMES` has two keys mapping to the same filename — silently breaks any future iteration

**File:** `src/sync/serializer.ts:31-41`
**Issue:** `SHARD_NAMES` deliberately carries BOTH a `fieldDefs` (camelCase) key and a `'field-defs'` (kebab) key, and both map to the identical value `'field-defs-000.json'`. This works today *only* because every consumer uses indexed access (`SHARD_NAMES[type]`) and never enumerates the object. The moment any future code does `Object.keys(SHARD_NAMES)`, `Object.values(SHARD_NAMES)`, or `Object.entries(SHARD_NAMES)` to drive a loop (e.g. "write every shard file", "GC every known shard name"), it will process `field-defs-000.json` twice and/or produce a key list that does not correspond 1:1 to manifest shard types. This is a structural footgun planted directly in the commit path. The serializer also writes the field-defs blob under `SHARD_NAMES.fieldDefs` (line 61) while the engine reads it under `SHARD_NAMES['field-defs']` (line 203) — the two-key arrangement is load-bearing for that aliasing, which makes the duplication non-obvious to remove later.
**Fix:** Collapse to a single canonical key and derive the alias explicitly, or add a guard test that asserts the value set has no unintended duplicates and documents the alias contract. Minimal hardening:
```ts
// Single source of truth; the engine maps the sync token to the name explicitly.
const FIELD_DEFS_SHARD = 'field-defs-000.json';
export const SHARD_NAMES = {
  people: 'people-000.json',
  maps: 'maps-000.json',
  markers: 'markers-000.json',
  groups: 'groups-000.json',
  'relationship-links': 'relationship-links-000.json',
  fieldDefs: FIELD_DEFS_SHARD,
  'field-defs': FIELD_DEFS_SHARD,
} as const;
// And add a regression test: any code that iterates SHARD_NAMES must be aware of the alias.
```
At minimum, add an inline assertion/test so a future `Object.keys` loop fails loudly rather than double-processing.

### WR-02: `reconcileOnOpen` deserializes all six shard slots per pulled type — masks shard-name mismatches

**File:** `src/sync/syncEngine.ts:276-287`
**Issue:** For each pulled type the engine calls `deserializeShards({ [SHARD_NAMES[type]]: blob })`, then reads only the one mapped field. `deserializeShards` attempts to parse all six slots; five are `undefined` and silently yield `[]` (serializer.ts:92). This means if `SHARD_NAMES[type]` is ever wrong for a type (e.g. a future rename desyncs the key the engine writes under vs. the key the serializer reads under), the pulled blob lands in NO field, `parseShard` returns `[]` for the intended type, and reconcile silently pulls an empty array instead of throwing. The bug would surface as silent data loss on a second device, not a crash. The current code is correct, but the per-type single-blob deserialize defeats the type-safety the serializer's keyed map is supposed to provide.
**Fix:** Either assert the blob was actually consumed (the intended field is non-undefined after deserialize), or deserialize by passing the blob keyed by the *known* serializer field rather than round-tripping through `SHARD_NAMES[type]`. Example guard:
```ts
const set = await deserializeShards({ [SHARD_NAMES[type]]: blob });
// Defensive: a non-empty cloud shard that deserializes to [] for `type` means the
// shard-name mapping desynced — fail loud rather than pulling empty.
```
At a minimum, add a reconcile test that pulls a NON-empty `relationship-links` and `field-defs` shard and asserts the records actually arrive (the existing field-defs round-trip test covers field-defs; relationship-links pull is untested).

### WR-03: Stale doc comments claim "three empty shard files" — now six; misleads future maintainers

**File:** `src/sync/syncEngine.ts:114-116` and `148-156`
**Issue:** `bootstrap()`'s docstring says it writes "three empty shard files" and `prepareOnOpen()`'s docstring repeats "the empty v0 manifest + three empty shards" / "bootstrap the v0 manifest + empty shards." The code now writes SIX shard files (people, maps, markers, groups, relationship-links, field-defs — `ENTITY_TYPES`, line 84-91). Doc drift in the corruption-proof commit core is a real maintenance hazard: a future reader trusting "three" may mis-reason about the bootstrap/reconcile invariants this phase depends on. This predates the phase (Phase 2 already added groups/relationship-links) but this phase touched the same function and left it stale.
**Fix:** Update both docstrings to "one empty shard file per `ENTITY_TYPES` entry (the five entity families plus `field-defs`)" so the count is not hard-coded and won't drift again.

## Info

### IN-01: `EntityTypeSchema` exported but consumed only internally within schemas.ts

**File:** `src/domain/schemas.ts:111`
**Issue:** `EntityTypeSchema` is `export`ed but is referenced only inside this module (by `FieldDefSchema` for `entityType`/`targetType`). If no external consumer needs it, the export widens the public surface unnecessarily.
**Fix:** Drop `export` unless a test or other module imports it; otherwise leave a one-line comment noting the intended external consumer.

### IN-02: `getDirtyTypes` runs six sequential `count()` queries instead of one pass

**File:** `src/sync/syncEngine.ts:362-372`
**Issue:** Each dirty-type check awaits a separate `db.<table>.filter(...).count()` serially. Functionally correct, and out-of-scope for v1 performance, but flagged as a quality note: as tables grow this is six full table scans on every push. Not a correctness defect.
**Fix:** Acceptable for v1; if revisited, run the six counts via `Promise.all` to at least parallelize, mirroring the `Promise.all` already used in `getEntities` (line 351).

### IN-03: Reconcile pulls and watermark-advances even for empty shards — intended but undocumented

**File:** `src/sync/syncEngine.ts:282-295`
**Issue:** `pulledHas` treats an empty pulled array (`[]`) as "pulled" (`!== undefined`), so the watermark advances for a type whose cloud shard is empty-but-newer. This is correct (it prevents re-pulling an unchanged empty shard every open), but the subtlety is undocumented and could read as a bug to a future maintainer.
**Fix:** Add a one-line comment at `pulledHas` (line 302) noting that an empty array is deliberately treated as a successful pull so the watermark advances.

### IN-04: `markSynced` receives the full entity set but only `dirtyTypes` were uploaded

**File:** `src/sync/syncEngine.ts:237` / `389-445`
**Issue:** `commit` passes the complete `entities` snapshot to `markSynced`, which iterates all six families. For families not in `dirtyTypes`, their records were never serialized/uploaded this commit, yet `markSynced` walks them. It is safe because a non-dirty record already has `dirty: false` so the `cur.dirty` guard skips it — but the function does more work than the commit's scope implies, and a future change to the dirty semantics could turn this into clearing a flag for content that was not uploaded.
**Fix:** No action required for correctness. Optionally scope `markSynced` to the serialized types, or document that the `cur.dirty && updatedAt`-match guard is what makes passing the full set safe.
