# Phase 02.1: Close gap DATA-03 — sync fieldDefs through the manifest cloud path - Research

**Researched:** 2026-06-26
**Domain:** Offline-first cloud sync (Dexie ↔ atomic manifest-swap SyncEngine), zod schema evolution, Vitest round-trip testing
**Confidence:** HIGH (entire fix surface is source-verified in-repo; no external dependencies)

## Summary

This is a surgical, code-only gap closure. Custom-field **definitions** (`db.fieldDefs`) already serialize into a `field-defs-000.json` shard (`src/sync/serializer.ts:55`) and round-trip through local export/restore, but the cloud manifest path silently drops them: `ENTITY_TYPES` (`src/sync/syncEngine.ts:73`) lists only the five entity families, and every cloud routine (`bootstrap`, `commit`, `reconcileOnOpen`, `getDirtyTypes`, `markSynced`) iterates that list or hand-enumerates those five tables. `ManifestSchema` (`src/domain/schemas.ts:136`) has no fieldDefs pointer. Net effect: on a second device or a fresh-session reconnect, entity custom *values* arrive with no *definitions* to render or validate them — the DATA-03 / STOR-02 / STOR-03 "own your entire database in your own cloud" guarantee is broken for the custom-field schema.

The fix must mirror the existing five-type wiring exactly — **symmetry, not novelty**. The one genuine design decision is the **type token**: the core `EntityType` union (`src/domain/types.ts:185`) is overloaded across the UI — `FieldDef.entityType` means "which entity family this field decorates" (people/maps/groups/relationship-links), and FieldManager/FieldEditor/repository all key Records on `EntityType`. **Adding `'field-defs'` to the core `EntityType` union would corrupt that domain meaning and ripple into ~8 UI/repo files.** The recommended approach is a *separate sync-shard-type token* (`SyncShardType = EntityType | 'field-defs'`) used only inside the sync engine + manifest, leaving `EntityType` semantically intact. The serializer already uses `fieldDefs` (camelCase) as its `SHARD_NAMES` key and `field-defs-000.json` as the file name; the manifest pointer key should match whatever token the engine iterates.

**Primary recommendation:** Introduce a sync-local `field-defs` shard token; thread it through `ENTITY_TYPES`/`getDirtyTypes`/`reconcileOnOpen`/`markSynced`/`bootstrap`/`commit` symmetric to the existing types; add an **optional** `'field-defs'` pointer to `ManifestSchema.shards` (optional = backward/forward compatible with old manifests); add one round-trip regression test (push on device A → fresh Dexie → `reconcileOnOpen` on device B → assert the FieldDef is present).

### Pattern 1: Symmetric shard wiring (the core of the fix)
**What:** Every place that hand-lists the five types must gain a sixth `field-defs` branch that mirrors the others exactly.
**When to use:** All six sync routines below.
**The token decision (HIGH confidence, source-verified):**
- `EntityType = 'people'|'maps'|'markers'|'groups'|'relationship-links'` (`src/domain/types.ts:185`) is **reused as `FieldDef.entityType`** (`types.ts:60`, the family a field belongs to) and as the key of `Record<EntityType, ...>` in `FieldManager.tsx:24,52`, `FieldEditor.tsx:30`, `repository.ts:152`, etc. **Do not widen it.**
- Introduce a sync-only union, e.g. `export type SyncShardType = EntityType | 'field-defs';` in `syncEngine.ts` (or `serializer.ts`), and retype `ENTITY_TYPES`, `getDirtyTypes`, `getShardMeta`, `setShardMeta`, `commit(dirtyTypes)` to it.
- `SHARD_NAMES` already has the slot: `SHARD_NAMES.fieldDefs = 'field-defs-000.json'` (`serializer.ts:34`). Note the **key is `fieldDefs` (camelCase)** there, while EntityType tokens are kebab. The plan must pick ONE token for the engine's iteration and map it to `SHARD_NAMES`. Recommended: use string token `'field-defs'` for the manifest/engine and map `'field-defs' → SHARD_NAMES.fieldDefs` (add `'field-defs': 'field-defs-000.json'` as an alias in `SHARD_NAMES`, or a small lookup), OR rename the `SHARD_NAMES.fieldDefs` key to `'field-defs'` to match — but renaming touches `serializeShards`/`deserializeShards` which currently reference `SHARD_NAMES.fieldDefs` by property. The lower-blast-radius choice is to keep the camelCase `fieldDefs` property and add a token→shard-name resolver in the engine.

**Exact change list per routine (file:line, current → required):**

1. **`ENTITY_TYPES` — `syncEngine.ts:73`**
   `const ENTITY_TYPES: EntityType[] = ['people','maps','markers','groups','relationship-links'];`
   → add `'field-defs'` and retype to `SyncShardType[]`. This single array drives `bootstrap()` (`:112`) and `reconcileOnOpen()` (`:246`), so both pick up field-defs automatically once the iteration body handles the token.

2. **`bootstrap()` — `syncEngine.ts:99-125`** iterates `ENTITY_TYPES` writing empty shards and building `shards: Record<EntityType, ShardPointer>` (`:111`). Retype the record to `Record<SyncShardType, ShardPointer>`. `serializeShards({... fieldDefs: []})` already emits the field-defs blob (`:103-110`), and `SHARD_NAMES[type]` must resolve for the `'field-defs'` token (see token decision).

3. **`commit()` — `syncEngine.ts:172-235`** `dirtyTypes` loop (`:184-191`) writes a new shard + pointer per dirty type. With `'field-defs'` in `dirtyTypes`, this works unchanged **iff** `SHARD_NAMES[type]` resolves and `shards` is typed `Record<SyncShardType, ShardPointer>` (`:181`). Step 5 `setShardMeta(type, now)` (`:217-219`) also covers field-defs automatically.

4. **`reconcileOnOpen()` — `syncEngine.ts:242-269`** iterates `ENTITY_TYPES`, reads `manifest.shards[type]` (`:247`), compares watermark, pulls + deserializes. **Two required edits:** (a) the per-type assignment block (`:256-260`) and `pulledHas()` (`:274-287`) must add a `field-defs → pulled.fieldDefs = set.fieldDefs` branch; (b) **EDGE CASE** `manifest.shards[type]` will be `undefined` for an OLD manifest with no field-defs pointer — guard with `if (!pointer) continue;` so an older manifest is a safe no-op, not a crash. `EntitySet` already has `fieldDefs` (`serializer.ts:20`) and `deserializeShards` already returns it (`serializer.ts:77`).

5. **`getDirtyTypes()` (Dexie port) — `syncEngine.ts:332-341`** hand-lists five tables. Add:
   `if ((await db.fieldDefs.filter((f) => f.dirty).count()) > 0) types.push('field-defs');`
   (`db.fieldDefs` already has a `dirty` index, `schema.ts:74`.)

6. **`markSynced()` (Dexie port) — `syncEngine.ts:358-404`** the `db.transaction('rw', [...])` table list (`:362`) omits `db.fieldDefs`; add it. Then add a `for (const f of synced.fieldDefs)` clear-dirty loop mirroring `:367-396` (match on `id` + `updatedAt`, clear `dirty:false` only when still matching — the CR-01 no-silent-edit-loss invariant). `getEntities()` already returns `fieldDefs` (`:321-329`) so `synced.fieldDefs` is populated.

7. **`upsert()` (Dexie port) — `syncEngine.ts:406-457`** the reconcile write path. Add `db.fieldDefs` to the transaction table list (`:407-413`) and an `if (entities.fieldDefs) { ... LWW put ... }` block mirroring `:415-454`. (Required so `reconcileOnOpen`'s pulled fieldDefs actually land in Dexie.)

8. **`makeMemoryPort` (test double) — `tests/sync/_memoryPort.ts`** mirrors the production port for the atomicity/prepareOnOpen tests. Its `getDirtyTypes` (`:26-34`), `markSynced` (`:38-56`), `upsert` (`:57-65`), `markAllDirty` (`:73-79`), `allClean` (`:80-88`) all omit `fieldDefs`. Extend them so the in-memory tests stay symmetric (otherwise field-defs dirty records are invisible to the memory-port tests).

### Pattern 2: Backward-compatible zod schema evolution
**What:** Add the field-defs pointer to `ManifestSchema` as **optional** so old manifests (no field-defs key) still `.parse()` clean.
**Source:** `src/domain/schemas.ts:136-150`. Current `shards` is a closed `z.object({people, maps, markers, groups, 'relationship-links'})`.
```typescript
// Source: derived from src/domain/schemas.ts:136-150 (zod 4.4.3)
shards: z.object({
  people: ShardPointerSchema,
  maps: ShardPointerSchema,
  markers: ShardPointerSchema,
  groups: ShardPointerSchema,
  'relationship-links': ShardPointerSchema,
  'field-defs': ShardPointerSchema.optional(), // NEW — optional = old manifests still validate (WR-03 precedent)
}),
```
**Why optional, not required:** A manifest written before this phase has no `field-defs` key. zod ignores *unknown* keys by default (see the `backups` comment at `schemas.ts:147-149`), but a **missing required** key would throw. Making it `.optional()` lets `readManifest` (`manifest.ts:25-31`) accept both old and new manifests. The first push after the fix writes the pointer; thereafter it is present.
**Compile-time lock:** `Manifest` type (`types.ts:207-211`) is `shards: Record<EntityType, ShardPointer>`. The `_manifestCheck satisfies` assertion (`schemas.ts:193`) will break unless `Manifest.shards` is widened consistently — change `Manifest.shards` to `Record<EntityType, ShardPointer> & { 'field-defs'?: ShardPointer }` (or `Partial<Record<SyncShardType, ShardPointer>>` with the five required), keeping the `satisfies` lock green.

### Anti-Patterns to Avoid
- **Widening core `EntityType` with `'field-defs'`** — corrupts `FieldDef.entityType` semantics and ripples into FieldManager/FieldEditor/repository/browse/profile. Use a sync-local token instead.
- **Making the manifest pointer required** — breaks `readManifest` on pre-existing cloud manifests (crash on second-device reconnect — the exact scenario this phase fixes).
- **Treating field-defs as a "schema, not entity" special case in the engine** — the serializer comment (`serializer.ts:23-27`) claims it "rides in reconcile" but that is false today; the simplest correct fix is to make it a first-class shard exactly like the others, then fix that overclaiming comment.
- **Forgetting the test double** (`_memoryPort.ts`) — leaving it un-extended makes field-defs invisible to the atomicity/prepareOnOpen suites and risks a false-green.

**Key insight:** The fieldDefs shard is *already produced and parsed*. The gap is purely that no cloud routine **iterates** it. The entire fix is "add the sixth branch everywhere the five are hand-listed," plus one optional zod key and one regression test.

## Common Pitfalls

### Pitfall 1: Older manifest has no field-defs pointer
**What goes wrong:** `manifest.shards['field-defs']` is `undefined`; `reconcileOnOpen` dereferences `pointer.updatedAt` → TypeError, crashing the open path (the exact second-device scenario).
**Why it happens:** Pre-fix cloud manifests predate the pointer.
**How to avoid:** `if (!pointer) continue;` before the watermark compare in the reconcile loop (`syncEngine.ts:247-249`), AND `ShardPointerSchema.optional()` in the schema so `readManifest` accepts it.
**Warning signs:** A test that seeds a v1 manifest (no field-defs) and calls `reconcileOnOpen` must NOT throw — include it.

### Pitfall 2: `EntityType` over-widening
**What goes wrong:** Adding `'field-defs'` to `types.ts:185` flows into `FieldDef.entityType`, `FieldManager`/`FieldEditor` `Record<EntityType,...>` maps, repository `DeletableEntityType`, etc., breaking exhaustiveness and producing a "field-defs" option in the field-family UI.
**How to avoid:** Sync-local `SyncShardType = EntityType | 'field-defs'` used only in `syncEngine.ts` + manifest types/schema.
**Warning signs:** `tsc` errors in `features/fields/*` or `features/profile/*` after the change indicate over-widening leaked.

### Pitfall 3: Token mismatch `'field-defs'` (kebab) vs `fieldDefs` (camel)
**What goes wrong:** `SHARD_NAMES` keys the field-defs slot as `fieldDefs` (`serializer.ts:34`) but EntityType tokens are kebab. If the engine iterates `'field-defs'` and does `SHARD_NAMES['field-defs']`, it is `undefined` → empty/garbage shard name.
**How to avoid:** Decide one token and provide a resolver. Lowest blast radius: keep `SHARD_NAMES.fieldDefs`, and in the engine map the `'field-defs'` token to `SHARD_NAMES.fieldDefs` (or add `'field-defs': 'field-defs-000.json'` as a second `SHARD_NAMES` entry).
**Warning signs:** A pushed manifest whose field-defs pointer references a file that deserializes empty.

### Pitfall 4: markSynced transaction omits db.fieldDefs
**What goes wrong:** Dirty flag never clears on field-defs → every push re-pushes them (harmless but noisy), OR if added to the clear-loop without adding the table to the `transaction('rw', [...])` list (`:362`), Dexie throws "table not in transaction."
**How to avoid:** Add `db.fieldDefs` to BOTH the transaction table array and the clear-dirty loop.

## Code Examples

### Round-trip regression test (the required acceptance proof)
Pattern lifted directly from `tests/sync/reconcile.test.ts:63-110` (the people round-trip) — the field-defs test is the same shape against `db.fieldDefs`.
```typescript
// Source: pattern from tests/sync/reconcile.test.ts:63-86 + serializer.entities.test.ts:33-45
// File to create: tests/sync/reconcile.fieldDefs.test.ts
import { afterEach, beforeEach, describe, expect, it } from 'vitest';
import { SyncEngine, createDexieRepoPort } from '@/sync/syncEngine';
import { InMemoryProvider } from '@/storage/memory/InMemoryProvider';
import { db } from '@/db/schema';
import type { FieldDef } from '@/domain/types';

function fieldDef(id: string, updatedAt: number, dirty = false): FieldDef {
  return { id, entityType: 'people', label: `field-${id}`, type: 'text',
           required: false, order: 0, deleted: false, updatedAt, dirty };
}
// beforeEach/afterEach clearDb() including db.fieldDefs.clear()  (see reconcile.test.ts:21-39)

it('round-trips a FieldDef: push on A → fresh Dexie → reconcileOnOpen on B pulls it', async () => {
  const provider = new InMemoryProvider();
  const folderId = await provider.ensureFolder('Relation Blueprint');

  // Device A: a dirty field definition pushed to the cloud.
  await db.fieldDefs.put(fieldDef('f1', 500, true));
  const engineA = new SyncEngine({ provider, folderId, repo: createDexieRepoPort(db) });
  await engineA.bootstrap();
  await engineA.push();
  const manifestFileId = engineA.manifestFileId();

  // Device B: simulate a fresh device — wipe local fieldDefs, then reconcile.
  await db.fieldDefs.clear();
  const engineB = new SyncEngine({ provider, folderId, repo: createDexieRepoPort(db), manifestFileId });
  await engineB.reconcileOnOpen();

  const pulled = await db.fieldDefs.get('f1');
  expect(pulled?.label).toBe('field-f1');   // the DEFINITION arrived → custom values are now renderable
  expect(pulled?.dirty).toBe(false);
});
```

## Open Questions

1. **Pull ordering: must DEFINITIONS arrive before VALUES?** (research Q5d)
   - What we know: Custom *values* live on each entity's `custom: Record<fieldId, value>` map (`types.ts:48`) and travel inside the people/maps/etc. shards. *Definitions* travel in the field-defs shard. The profile/form read paths fetch defs live via `listFieldDefs(entityType)` (`CustomFieldRows.tsx:203`, `EntityForm.tsx:177`) and already tolerate a missing def (render "(removed)", guard `(custom ?? {})[id]` — Phase 2 UAT-BLK, `02-VALIDATION.md:63`).
   - What's unclear: Nothing functional — order is tolerated. `reconcileOnOpen` upserts whichever shards are newer in a single pass; both can arrive same reconcile.
   - Recommendation: **Either order is safe.** No ordering constraint needed in the plan. Optionally add field-defs to the iteration before the entity types for tidiness, but it is not load-bearing.

2. **Token spelling for the manifest pointer key.**
   - Recommendation: use `'field-defs'` (kebab, consistent with the other manifest keys like `'relationship-links'`) for the manifest/schema, and resolve it to `SHARD_NAMES.fieldDefs` in the engine. This keeps the manifest JSON self-consistent and the serializer untouched.
