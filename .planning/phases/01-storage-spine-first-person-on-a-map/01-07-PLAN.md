## Phase Goal

**As a** single curator of a private people-and-places dataset, **I want to** connect my own Google Drive, create a person, place them on an image-map, open their profile, and export then restore my whole database, **so that** I own my entire database in my own cloud with no server and can trust the storage spine before I put real data in it.

## Acceptance Criteria (this plan — the safety net)
- [ ] Export produces a self-contained backup of shards + media (EXPT-01).
- [ ] Restore reconstitutes the DB including photos, validated by zod (EXPT-02).
- [ ] ROUND-TRIP: export -> wipe -> import deep-equals entities + byte-equals every photo.

<objective>
Build the export/restore slice and its mandatory round-trip property test — the safety net for the entire phase, since the cloud is the only copy. Export bundles every entity + every media blob into a portable, self-contained file; import validates it with zod and restores it inside an all-or-nothing transaction; the round-trip is a tested automated assertion (deep-equal entities + byte-equal photos), not export theater.

Purpose: EXPT-01/EXPT-02 exist precisely because Drive is the only durable copy — a tested restore must exist before real data goes in. RESEARCH Pitfall 6 ("export theater") demands the round-trip be an automated assertion. This is the second of the two highest-value tests in the phase.
Output: `src/features/backup/*`, the test fixtures (sample photos + DB generator), and the export/round-trip tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| imported backup file -> Dexie | A user-supplied file (possibly foreign or corrupt) is parsed and applied to the database |
| export file -> user's filesystem | The whole database (incl. personal data + photos) leaves the app as a portable file |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Tampering | Imported backup bundle | mitigate | `BackupSchema.parse` validates the whole bundle before any write; a corrupt/foreign file is rejected with current data untouched (RESEARCH ## Security Domain V5) — asserted by the corrupt-file test |
| T-07-02 | Denial of Service / data loss | Partial restore | mitigate | Restore runs in a single Dexie `rw` transaction (all-or-nothing); a failure mid-restore rolls back |
| T-07-03 | Denial of Service / data loss | Accidental destructive restore over unsynced local work | mitigate | Explicit destructive ConfirmDialog with an "export first" nudge (UI-SPEC A11) |
| T-07-04 | Information Disclosure | Exported backup contains unencrypted personal data + photos | accept | v1 boundary: provider/file security only, no app-level encryption (SEC-01 deferred to v2) — the export's portability is the point; documented limitation |
</threat_model>
