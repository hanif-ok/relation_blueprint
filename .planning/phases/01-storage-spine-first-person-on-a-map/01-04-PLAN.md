## Phase Goal

**As a** single curator of a private people-and-places dataset, **I want to** connect my own Google Drive, create a person, place them on an image-map, open their profile, and export then restore my whole database, **so that** I own my entire database in my own cloud with no server and can trust the storage spine before I put real data in it.

## Acceptance Criteria (this plan)
- [ ] Photos are thumbnailed client-side and stored as content-addressed media blobs (PROF-03).
- [ ] A person's profile shows a thumbnail + multi-photo gallery (PROF-02).
- [ ] Identical image bytes dedupe to one media record.

<objective>
Add the media slice on top of the Walking Skeleton: client-side thumbnail generation (round avatar + capped gallery image), a content-addressed blob store (hash -> Blob in the unindexed Dexie `media` table), the multi-photo upload control in the person form, and the lazy-loaded photo gallery in the profile sidebar.

Purpose: PROF-02/PROF-03 require thumbnails generated in-browser (no server, no paid service) and stored as media blobs the user owns. Content addressing makes media idempotent and dedupes re-uploads, which the Plan 05 sync engine relies on to avoid re-uploading unchanged photos. This widens the existing person/profile slice rather than adding a new layer.
Output: `src/media/*`, the `PhotoGallery` and `PhotoUpload` components, and the media unit tests.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Denial of Service | Oversized photo upload | mitigate | `capGalleryImage` downscales large images before storage; avatar thumbnailed to 96px — bounds memory/quota growth |
| T-04-02 | Information Disclosure | Photo blobs at rest | accept | v1 boundary: provider-level security only, no app-level encryption (SEC-01 deferred to v2) — documented limitation |
| T-04-03 | Tampering | Content-addressed media filenames | mitigate | SHA-256 content hash is the filename; mismatched bytes produce a different hash, so a tampered blob cannot masquerade as another (immutable, idempotent) |
</threat_model>
