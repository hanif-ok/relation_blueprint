<objective>
Fix GAP 1 (MAJOR): a clean Drive connect on an EMPTY database errors with "sync failed, please retry" instead of reaching "synced". Root cause (confirmed in .planning/debug/empty-state-first-sync.md): `useSyncEngine.onConnected` constructs a `SyncEngine` with no `manifestFileId` and immediately calls `engine.reconcileOnOpen()`, whose first statement (`manifestFileId()`) throws "manifest not initialized — call bootstrap() first" because `_manifestFileId` is null. `bootstrap()` only runs inside `push()`, which is only scheduled by a LATER edit — so the empty first connect throws before any Drive REST call and `onConnected`'s catch maps it to `markError` → the error chip.

This plan adds the missing initialization step: establish (discover-or-bootstrap) the manifest BEFORE `reconcileOnOpen()` runs. It uses the PREFERRED fix direction from the diagnosis — discover an existing `manifest.json` in the app folder first and only bootstrap when none is found — which also enables silent re-adoption of an existing cloud DB on a second device.

Purpose: Restore trust in the storage spine — a first connect before any data exists must succeed quietly, and reconnecting to a folder that already holds a database must adopt it, not re-bootstrap over it.
Output: A `prepareOnOpen()` method on `SyncEngine`, an updated `onConnected` that calls it before reconcile, and a strengthened regression test that asserts the empty-DB connect reaches 'synced' with no `markError`.
</objective>

  <files>src/sync/syncEngine.ts</files>
  <behavior>
    - Given a folder with NO manifest.json: prepareOnOpen() bootstraps (writes v0 manifest + 3 empty shards) and sets the engine's manifest file id; a subsequent reconcileOnOpen() is a clean no-op (v0 updatedAt=0 ≤ local watermark 0 ⇒ all types skipped).
    - Given a folder that ALREADY contains a manifest.json (e.g. written by a prior push from a "first device"): prepareOnOpen() adopts the existing manifest's file id WITHOUT calling bootstrap() — no new manifest or shard files are written; the existing manifest is left byte-identical.
    - prepareOnOpen() is idempotent and a no-op when the engine was constructed with (or already resolved) a manifestFileId.
  </behavior>
  <action>
    Add a public async method `prepareOnOpen()` to the `SyncEngine` class. It must ensure `_manifestFileId` is set before any reconcile/push runs, using discover-then-bootstrap:
    1. If `this._manifestFileId` is already set, return immediately (idempotent — preserves a provided/already-resolved id).
    2. Otherwise call `this.provider.list(this.folderId)` and look for an entry whose `name` equals the existing `MANIFEST_NAME` constant ('manifest.json'). If found, set `this._manifestFileId` to that entry's `id` and return — DO NOT call `bootstrap()` (this is the silent re-adoption path; it must never overwrite or duplicate the canonical manifest).
    3. If no manifest entry exists, call `await this.bootstrap()` (the existing idempotent method that writes the v0 manifest + three empty shard files). This is the empty-first-connect path.
    Keep the existing `bootstrap()` and `manifestFileId()` methods unchanged — `prepareOnOpen()` composes them; it does not replace the bootstrap guarantee. Add a concise doc comment on the new method explaining the discover-then-bootstrap order and that it is the connect-time initialization step that `reconcileOnOpen()` requires. Reuse the existing module-level `MANIFEST_NAME` constant for the filename match (per the manifest-swap design in 01-05-SUMMARY); do not hardcode a second literal.
    Do NOT change the commit sequence, the manifest overwrite as the sole commit point, or validate-before-write. `prepareOnOpen()` only adds a non-destructive read (provider.list) plus the already-safe idempotent bootstrap.
  </action>
